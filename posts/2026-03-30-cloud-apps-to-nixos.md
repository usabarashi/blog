マネージド実行基盤で動かしていたアプリをオンプレの NixOS ホストに移し, ログはクラウドに残しました.
DB もオンプレへの移行を予定していますが, データの性質と必要なサービス水準によってはクラウドに残します.
個人利用の **Homelab** で, ホスト 1 台を運用する構成を前提にしています.
この記事では, アプリ, ログ, DB の配置とその理由を説明します.

![実行はオンプレの NixOS, DB とログはいまクラウド](/images/2026-03-30-cloud-apps-to-nixos-split.svg)

## アプリを NixOS に移した理由

クラウドの利用料は基本的に無料枠に収まっており, 費用の削減が移行の主な目的ではありません.
移した理由は, 既存のホストでアプリを常時稼働させられることです.
移行当時に利用していた Terraform Cloud Free のリソース数の上限も, 移行を後押ししました.
実行設定を NixOS にまとめることで, クラウド側で管理する設定や権限を減らせます.
一方で, ホストの監視や障害復旧は自分で担います.

アプリは基本的にステートレスで, 永続化が必要な状態は DB に保存します.
アプリを実行できる別の NixOS ホストにも, 同じアプリ構成を適用できます.
クラウド上の NixOS の VM も移行先にできます.
移行先では, 秘密情報と DB への接続・認証を別途用意します.

## DB の置き場所

状態はいまクラウドのマネージド DB に保存しています.
ホストを再インストールしても, ホストのディスクが壊れても, DB に保存済みの状態は残ります.
バックアップの保持期間やアクセス権は自分で設定し, 復旧手順も確認します.

DB もオンプレへの移行を予定していますが, データの性質と必要なサービス水準によってはクラウドに残します.
判断基準は, データの重要性と再構築の可否, 許容できる停止時間とデータ損失の範囲です.
候補となる構成ごとに, バックアップや冗長化の仕組みと復旧手順が, これらの要件を満たせるか確認します.

オンプレでこれらの要件を満たせるなら移行し, 難しければクラウドに残します.
失っても再構築できるデータは, オンプレへ移しやすいです.

オンプレへ移すと, データを手元に置けます.
一方で, ストレージの管理やバックアップ, 復旧を自分で担います.

DB をクラウドに置く場合, アクセスは拠点の回線とクラウド側の可用性に依存します.
読み書きの頻度や処理方式によっては, 通信の遅延が制約になります.
クラウドの SLA は対象サービスについてのもので, アプリ全体の可用性を保証するものではありません.
アプリ全体の可用性は, ホストや回線, DB など, 動作に必要な構成要素に依存します.

## ログはクラウドに

ログをホスト内だけに保存すると, ホストの停止時に確認しにくくなります.
停止前にクラウドへ転送したログは, ホストが停止しても確認できます.
アラートもログに基づいてクラウド側で設定します.

ログをホスト内に長期間保持すると, ディスク容量を圧迫します.
クラウド側で長期保持と検索を行えば, ホスト内の保持量を抑えられます.
ログの保存と検索も, 基本的にクラウドの無料枠の範囲で使っています.

転送が止まっているあいだのログを残すには, ホスト側のバッファと再送が必要です.
バッファの容量超過やディスク故障などにより, 未転送のログを失う可能性があります.

## クラウドへの認証は ID 連携で

クラウド API 用の長期アクセスキーをホストに配布せず, ID 連携で短命の資格情報を取得します.
取得した資格情報が漏えいしても, その有効期限によって悪用され得る期間を限定できます.
ただし, ホストが侵害されると資格情報を再取得されるおそれがあるため, 侵害時は連携に使う ID の無効化や信頼設定の変更などで, 新たな資格情報の取得を止めます.
発行済みの資格情報についても, 有効期限やサービス側の失効手段を考慮します.
ID 連携の設定は, NixOS のモジュールとクラウド側の設定で管理します.

## モジュールで境界を表す

アプリのリポジトリには, コードとともに NixOS モジュールを用意しています.
モジュールには, systemd サービスやタイマー, プロセスの隔離に関する設定と, 独自の設定項目（options）を定義しています.
ホスト側は, アプリのリポジトリを flake の入力に追加し, 公開された NixOS モジュールを imports に指定して設定します.

Terraform では同じディレクトリの設定ファイルを一つのモジュールとして扱います.
NixOS では, 機能ごとに分けた設定を imports で組み合わせます.

この構成では, 実行の設定はアプリのモジュールに, 接続先の設定はホストの構成に置いています.

![アプリのリポジトリが配る NixOS モジュールと, ホスト側の設定](/images/2026-03-30-cloud-apps-to-nixos-module.svg)

アプリのコードには, 配置先に固有の接続設定を埋め込みません.
接続先は, モジュールが用意する option にホスト側で値を入れ, 環境変数などでアプリに渡します.
認証に必要な情報は, 認証ファイルなどで別途渡します.
秘密情報は Nix の設定値に直接書かず, Nix ストアの外で管理して実行時に渡します.
接続先をコードから分離することで, 配置を変えるときのアプリ側の修正を減らせます.

## 障害時に何が残るか

現在の構成では, ホストが停止してもクラウドに保存済みのデータとログは残ります.
未送信のログや処理途中のデータは失われる可能性があります.
ホストの停止や回線断の検知には, 外部からの死活監視などが別に必要です.

回線が切れると, アプリはクラウドの DB へのアクセスやログの転送ができなくなります.
ホスト内で完結し, 外部サービスの接続失敗に影響されない処理は継続できます.

DB をアプリと同じホストへ移す場合は, ホストの故障で両方が停止します.
別ホストに置く場合も, 共通する電源や回線の障害を考慮します.
バックアップの保存先も含めて, 共通の障害で失われる範囲と復旧手順を設計します.

現在, アプリを動かすホストは 1 台です.
電源とディスクは, アプリの共通の障害点になります.
リソースも共有するため, 重い処理を追加するときは cgroup で CPU やメモリの使用を制限します.

## この分割が向かない場合

ログを外部に出せない場合は, 許容される環境の中にログ基盤を置きます.
アプリと同じホストに置くか, 別のオンプレホストに分離します.
保持期間と, 障害時に失う範囲を決めておきます.

クラウドの ID 基盤を使えない場合は, 利用できる ID 基盤と資格情報の管理方法を選びます.
長期的に使う認証鍵をホストに置くなら, 更新・失効の手順を決め, 権限を必要最小限に制限します.

負荷が単一ホストを超える場合は, ホストの増設とクラウドへの移行を比較します.
複数の拠点で同じアプリを動かす場合も, 実行の置き場所を選び直すきっかけになります.

## 雑感

個人の Homelab では, 可用性を作り込むより, 障害時に何が残るかを決める方が大事でした.
アプリの実行環境は NixOS の構成から再構築し, 保存済みの状態とログはクラウドに残す, という分担です.
DB もオンプレへ移す予定ですが, そのときはバックアップと復旧の設計が中心になります.

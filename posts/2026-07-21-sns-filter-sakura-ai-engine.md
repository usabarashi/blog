X の検索結果を Slack に流す bot は, 投稿を残すか落とすかを LLM に判定させています.
判定は Gemini からホスト上の llama.cpp を経て, 今回さくらの AI エンジンへ移しました.
判定は 20 分に 1 回, 1 リクエストで終わり, 求めるのは規則の適用と出力形式の維持です.
移行ではモデルの規模より, 無料枠と待ち時間, ホストの負担を重視しました.

![systemd タイマーで起動した bot が投稿をまとめて送り, 判定を通ったものだけを Slack に流す. llama.cpp コンテナは削除した](/images/2026-07-21-sns-filter-sakura-ai-engine.svg)

## 判定の仕様と評価

投稿を `[0] @screen_name: 本文` の形式で並べ, 投稿ごとに残すか落とすかを返させます.

| 項目 | 決めていること |
| --- | --- |
| 入力 | 1 回の検索結果をまとめた 1 メッセージ |
| 出力 | 各投稿の index と keep を持つ JSON |
| 件数 | 入力と同じ件数 (JSON Schema で固定) |
| 温度 | 0 |
| 失敗時 | 判定対象の投稿をすべて Slack に流す (fail open) |

規則は自然文で書き, 技術的な内容を残し, 話題の外れた投稿, 内容の薄い感想, リンクだけの投稿, 宣伝を落とします.
規則には KEEP と REMOVE の例を付けます.

評価用サンプルには KEEP, REMOVE, BORDERLINE を置き, 一致率は BORDERLINE を除いて計算します.
BORDERLINE は規則が決めない投稿なので, そこで競ってもラベルの揺れを測るだけです.
誤りは, 誤って落とす場合と, 落とすべき投稿を残す場合に分けます.
誤って落とした投稿は Slack に現れず, 検索のしきい値も進むので, あとから拾えません.

以前の移行では, Gemini の代わりに置いた Qwen3-1.7B-Q8 が 17 件で 82.4% 一致しました.
17 件では 1 件が約 6 ポイントなので, 候補を絞ったら数十件に増やします.

## ローカル推論の費用

移行前は, ホストの nspawn コンテナで Qwen3-4B の Q4_K_M を CPU だけで動かしていました.
以前の 1.7B から 4B に替えた構成です.
2 つの bot が 1 つのコンテナを共有し, 実行のたびに起動してモデルを読み込み, 最大 90 秒の起動待ちと停止の制御が必要でした.
費用は請求書に現れず, メモリ, CPU, 起動待ちで払っていました.
メモリ上限 7 GiB はホストの約半分で, コールドスタートでは最初の判定に 60-80 秒かかりました.
1.7B で 60 件を判定すると 9-13 分かかった記録があり, 当時のタイムアウト既定値は 900 秒でした.
移行前は 300 秒に短縮しており, 件数が多い回はこの上限に届く可能性がありました.

| | ローカル (llama.cpp) | さくらの AI エンジン |
| --- | --- | --- |
| モデル | Qwen3-4B-Q4_K_M | Qwen3-Coder-30B-A3B-Instruct |
| 計算資源 | ホストの CPU 2 スレッド, メモリ上限 7 GiB | クラウド |
| 起動待ちの確認 | `/v1/models` を 90 秒まで | 不要 |
| タイムアウト | 300 秒 | 120 秒 |
| 費用 | ホストの資源を消費 | 無料枠の範囲で 0 円 |

## さくらの AI エンジンに移す

[![さくらの AI エンジンの公式ページ](https://ai.sakura.ad.jp/images/sakura-ai/ogp.png)](https://ai.sakura.ad.jp/sakura-ai/ai-engine/)

さくらの AI エンジンは OpenAI 互換の Chat Completions を提供し, 接続先は `https://api.ai.sakura.ad.jp`, 認証は Bearer の API トークンです.
bot は llama.cpp と同じ形式で話していたので, 認証ヘッダを足すだけで済みました.
トークンは管理画面で発行し, 秘密情報のリポジトリから `LLM_API_KEY` として渡します.
トークンは bot ごとに分けています.

移行では, ホスト側のモジュール, 停止の判断, コンテナへの依存, LAN 内の DNS 名, メモリ上限の調整を削除しました.
`/v1/models` の probe は, モデル読み込みの待ちが不要になり, 認証を要求する AI エンジンでは 401 になるため削除しました.
クラウド側の混雑に備えてタイムアウトは 120 秒にし, fail open は変えていません.

## 無料枠に収まるかの見積もり

無料枠はモデルごとに月間リクエスト数が決まっており, 移行時点の資料ではこのモデルは月 3,000 でした.
枠内なら費用は 0 円で, 超えるとレート制限が返り, 有料プランへ自動では切り替わりません.
20 分間隔なら 30 日で 2,160 回 (72%), 10 分間隔なら 4,320 回 (144%) です.
検索結果が空の回は送らず, この数は定時実行だけで評価や再試行を含みません.
2 つの bot を合わせると 30 日で 4,320 回になり, 1 つの枠に数えられるなら超えます.
無料枠がアカウントやプロジェクトで共有されるのか, API トークンごとに分かれるのかは, いまの構成でも確かめる必要があります.

投稿ごとに送る場合, 毎回 50 件なら 1 日 3,600 リクエストで枠を超えます.
1 回を 1 リクエストにまとめているので, 投稿が増えても消費は 1 回のままです (まとめられる件数の範囲で).

枠を超えたときの失敗はログに残りますが, Slack の投稿だけでは原因を判断できません.
判定の失敗と, 入力と通過の件数の比を見ます.

## 過剰品質を見分ける

判定の質は, モデルの一般評価ではなく評価用サンプルで測ります.
世界知識や多段の推論が効くかも同じサンプルで確かめます.
費用は料金だけでなく, 待ち時間, ホストの資源, 運用の手間も含めて比べます.
無料枠は呼び出し回数, トークン課金は入出力の長さと単価が効きます.

より低コストの候補で要求を満たせるなら, 高いモデルは要りません.
今回は同じサンプルで比べていないので, 30B が必要か, 過剰かはまだ判断できません.

選ぶときは仕様を書き, 明確な例と曖昧な例にラベルを付け, 候補の一致, 誤りの内訳, 所要時間を測ります.
明確な例で差が出ず, 周期と枠に収まるもののうち, 最も安いものを選びます.
規則を変えたら測り直します.
誤削除の費用が高い使い方では, 一致率だけでなく誤削除の少なさを重視し, 評価で差が見えるモデルの費用を払います.

30B は無料枠の対象で, 既存のリクエスト形式のまま接続できたため選びました.
移行で確認できたのはローカル推論基盤の管理を省けることで, モデルの大きさは評価で決め直せます.

## 雑感

推論をクラウドへ移し, ホストからはコンテナと起動待ちを消しました.
選んだモデルが要求を満たすかは, 今後, 評価用サンプルで確認し, 判定の失敗と, 入力と通過の件数の比を見ます.

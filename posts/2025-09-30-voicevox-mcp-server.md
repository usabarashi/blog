[`voicevox-cli`](https://github.com/usabarashi/voicevox-cli) は, 私が作っている CLI で, VOICEVOX Core を使った日本語の **TTS**（text-to-speech）を行います.
同じリポジトリから `voicevox-mcp-server` という実行ファイルもビルドでき, **MCP**（Model Context Protocol）のクライアントから音声合成を呼べます.

## プロセスの分割

この構成では, MCP クライアントを内包するホストアプリ, MCP サーバ, `voicevox-daemon` のあいだに 2 つの境界があります.
MCP クライアントとサーバのあいだは stdio で, 改行で区切った JSON-RPC のメッセージをやり取りします.
MCP サーバとデーモンのあいだは Unix ドメインソケットです.

![プロセスの分割と 2 つの境界](/images/2025-09-30-voicevox-mcp-architecture.svg)

デーモンは, 起動時に ONNX Runtime と OpenJTalk の辞書を読み込み, VOICEVOX Core を初期化します.
話者とスタイルの一覧, およびスタイル ID からモデルへの対応も, このときに作ります.
この初期化を合成要求のたびにやり直すのは避けたいので, デーモンを常駐させ, CLI の `voicevox-say` からも MCP サーバからも同じデーモンに繋ぐ形にしました.

stdio で繋ぐ場合, ホストアプリは MCP サーバを子プロセスとして起動します.
サーバの寿命とデーモンの寿命を分けておけば, 接続のたびに初期化をやり直さずに済みます.

合成要求の処理では, 対象の声のモデルを読み込み, 合成後にアンロードを試みます.
モデルを常駐させれば次の読み込みは省けますが, そのあいだメモリを占有し続けます.
ツールが頻繁に呼ばれる用途よりも, 間隔を空けて読み上げる用途を想定しているので, モデルを保持し続けず, 要求ごとにアンロードする設計にしました.

ソケットは, 既定では `$XDG_RUNTIME_DIR/voicevox-daemon.sock` に置きます.
`$XDG_RUNTIME_DIR` が設定されていなければ `$XDG_STATE_HOME`, それも無ければ `~/.local/state` の下です.
`HOME` も無ければ `/tmp` に置きます.
`VOICEVOX_SOCKET_PATH` で変えられます.
変える場合は, ソケット専用のディレクトリを作り, MCP サーバを動かす利用者の所有で, パーミッション `0700` にしておくことを推奨します.
`/tmp` のような共有のディレクトリに置くと, 環境やソケットの権限によっては, 他の利用者からも合成を頼めるおそれがあります.

MCP サーバは, ツールの引数を検証し, デーモンに合成を頼み, 返ってきた音声を再生します.
合成そのものはせず, 会話の履歴も保持しません.

起動時にデーモンを起こし, 失敗しても警告を出して動き続けます.
デーモンに接続できないあいだは, デーモンを必要とするツールの呼び出しがエラーになります.

## ビルドと依存物の取得

CLI と MCP サーバは, Nix の flake からビルドします.
デーモンが使う ONNX Runtime, OpenJTalk の辞書, 声のモデルは, リポジトリには入っていません.
これらは Nix のビルドでは取得せず, `voicevox-setup` というインストーラーが配布元からダウンロードして XDG のデータディレクトリ（既定は `~/.local/share/voicevox`）に置きます.

## instructions

**instructions** は, MCP の `initialize` 応答に含めてサーバがクライアントへ渡す, サーバの使い方の説明です.
このサーバでは, その内容を `VOICEVOX.md` に書いています.
状況に応じたスタイル ID の選び方, 呼び出しの間隔, 失敗したときの振る舞いなどです.
クライアントがこれをモデルに提示するかはホストアプリの実装次第で, サーバは内容を渡すところまでを担います.

たとえば, 「処理が一段落したら ID 1（あまあま）で結果を読み上げ, 作業が難航しているときは ID 76（なみだめ）で状況を説明する」という方針を書けます.
エージェントがこの方針に沿ってツールを呼べば, 画面を見ていなくても進み具合や詰まりを把握しやすくなります.

`VOICEVOX.md` は差し替えられます.
`VOICEVOX_MCP_INSTRUCTIONS` で指定したファイルが最優先で, 次に `$XDG_CONFIG_HOME/voicevox/VOICEVOX.md`（`XDG_CONFIG_HOME` が未設定なら `~/.config/voicevox/VOICEVOX.md`）, その次が実行ファイルと同じディレクトリの `VOICEVOX.md`, 最後にカレントディレクトリの `VOICEVOX.md` です.

## 引数の検証とテキストの分割

ツールは 2 つあります.
`list_voice_styles` と `text_to_speech` です.
`text_to_speech` の引数は `text`, `style_id`, `rate`, `streaming` で, `text` と `style_id` が必須です.

`text_to_speech` では, 合成をデーモンに頼む前に引数を検証します.
空のテキスト, 0.5 から 2.0 の外の `rate`, 10,000 バイトを超えるテキスト, 1000 を超える `style_id` はここでエラーになります.
`style_id` の一覧は `list_voice_styles` で取れます.
1000 以下でも, 存在しない ID はデーモン側でエラーになります.

`streaming` は既定で true です.
この場合, テキストを `。`, `！`, `？`, `．`, 改行で区切り, 区間ごとにデーモンへ合成を頼みます.
区切りが現れないまま 100 文字に達したら, 直前の読点, 半角カンマ, 空白の位置で分けます.
それも無ければ 100 文字の位置で分けます.
全文の合成完了を待たず, 合成できた区間から順に再生します.

`streaming` が false なら, テキスト全体を 1 回で頼みます.

制限値と分割の設定を表にします.
パスは, 対象にしたコミットのものです.

| 項目 | 値 | 定義箇所 |
|---|---|---|
| 合成するテキストの長さ | 10,000 バイト | `src/mcp/tools.rs` |
| `style_id` の上限 | 1000 | `src/mcp/tools.rs` |
| 長さによる分割の閾値（既定） | 100 文字 | `src/synthesis/streaming.rs` |

## MCP の応答と音声の再生

音声は MCP の応答に含めません.
`text_to_speech` の呼び出しで MCP の境界を越えるのは, テキストや合成条件を含む要求と, 結果を伝える短いテキストです.

この構成では, クライアントが同じマシン上でサーバを起動する使い方を想定しています.
合成した音声は, サーバが動くマシンの音声出力から鳴らすので, クライアントに音声を渡さずに読み上げられます.

ツールの応答は結果を伝える短いテキストなので, モデルに渡す情報量を小さく抑えられます.
クライアント側に音声のデコードや再生の実装も要りません.

音声をクライアント側で鳴らす設計も考えられます.
WAV を base64 にすると, データは約 4/3 倍に膨らみます.
たとえば 24 kHz, 16 bit, モノラルの非圧縮 PCM なら, 10 秒で約 480 kB, base64 にすると約 640 kB です.
クライアントには音声の受け口と再生の実装が要ります.
音声を応答に含める設計では, ホストアプリがそれをモデルへ渡すか, どの形式で渡すかによって, モデルの文脈の使われ方が変わります.

## この構成の弱点

再生するのはサーバが動くマシンなので, 別のマシンで音を出すには, 音声をクライアントへ渡すか, サーバ側に別の出口を作るかになります.

再生処理が完了しても, 音が実際に利用者へ聞こえたかまでは確認できません.

同じサーバで 2 つの呼び出しが同時に再生に入ると, 音が重なります.
再生を直列化する仕組みはありません.

## 残課題

サーバ側のコードには, `notifications/cancelled` を受け取り, 対象のツール呼び出しに伝え, 再生を止めてツールの処理を終える経路があります.

ただし, 私が試した範囲では, 呼び出し側でキャンセルしても再生が続きます.
通知が届いていないのか, 届いても止まらないのかは切り分けられていません.

ホストアプリや MCP クライアントからの通知に頼らず再生を止める手段も, 今後の検討課題です.

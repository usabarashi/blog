オンプレミスのサーバは Nix で, クラウドのリソースは Terraform で管理しています.
一方で, 個別のガジェットの設定は, 管理画面を手で操作していました.
UPS もその 1 つで, APC の GS Pro 500 には設定用の API が見つかりませんでした.
IaC で管理したいので, 管理画面の HTML から設定を読み取り, フォームを送信する Terraform Provider を作りました.
個人利用のためのツールなので, ソースコードは公開していません.

## UPS の設定を IaC に載せる

UPS の設定は, 停電したときに何をどの順で止めるか, スマートコンセントの起動をどれだけ遅らせるか, 監視の宛先をどこにするかといったものです.
Homelab の構成の一部なので, ホストの構成と同じように Git で管理したいところです.
これまでは Web の管理画面を操作して設定を変えていたので, 変更内容が Git に残りませんでした.

## 使用機器と観測した挙動

| 項目 | 内容 |
|---|---|
| 機種 | APC GS Pro 500 |
| ファームウェア | NMC v6.0.4 |
| コンセント | マスター, バックアップ, スマート 2 口 |
| 設定方法 | Web の管理画面 |
| HTTP 接続時の観測 | 複数接続が重なると 403 が返ることがある（復旧まで約 5 分） |
| 今回使用した通信方式 | 平文の HTTP |
| メール通知時の観測 | iCloud の SMTP サーバへ直接送ると TLS 接続に失敗 |

## セッション管理

Terraform はリソースの操作を並列に進めます.
GS Pro 500 では, 複数の接続が重なると 403 が返ることがありました.

そこで, Terraform Provider プロセス内の操作をミューテックスで直列化し, ログインはプロセスごとに最初の 1 回だけにして, そのセッションを使い回しています.
この直列化が効くのは, 同じプロセスの中だけです.
同時に走る別の run や, 管理画面からの操作までは排他できません.

![plan / apply 時のセッションの扱い](/images/2026-02-22-terraform-provider-apc-session.svg)

HTTP の接続とログインのセッションは別です.
HTTP の keep-alive を無効にして接続は要求ごとに閉じますが, 認証済みのセッション ID は後続の要求でも使い回します.

Terraform Provider には, SIGTERM を受けたときにログアウトする処理を入れています.
この処理が動かずに終わった場合は, セッションが GS Pro 500 側のタイムアウトまで残ることがあります.

接続が切れたり 5xx が返ったりすることもありました.
そのため, ページの取得は 3 回まで試し, 待ち時間を 2 秒, 4 秒と伸ばしています.
403 が返ったときは再試行せず, 時間を置いて実行し直します.

ログインの成否は, 応答の HTML で見ています.
GS Pro 500 は, 認証に失敗したときもセッションが切れたときも, エラーのステータスではなく 200 でログイン画面を返します.
そのため, HTTP ステータスコードだけでは認証の成否を判定できません.
認証後のページを期待した要求にログイン画面が返った場合は, 処理をエラーにします.
そのうち, 入力の誤りを伝える文言がある場合は, 認証情報の誤りとして扱います.
フォームの送信中にログイン画面が返った場合は, セッション切れとしてエラーにします.

## Web フォームをプログラムから読み書きする

GS Pro 500 の管理画面は複数のページに分かれていて, 設定はページ上のフォームで変えます.
Terraform Provider では, 属性名の接頭辞で設定を 18 の設定グループに分けています.
属性名は `email_from_address` のように接頭辞と項目名を組み合わせた形で, この場合は `email_` がメール設定グループを示します.
設定グループはおおむねページやフォームに対応しますが, 1 つのページに 2 つのグループがあったり, 1 つのグループが複数のフォームに分かれていたりします.

読み取りは, ページを取得し, 名前でフォームを選び, テキスト欄や選択肢の値を取り出します.
書き込みは, 同じページを取り直し, 取得したフォームを土台にして, 対象の設定グループの値を差し替えて送ります.
グループが複数のフォームに分かれている場合は, そのすべてを送ります.
変えるフィールドだけを POST するのではなく, フォーム全体を組み直して送ります.
送信に必要な隠しフィールドはページごとに違いますが, 取得した値を保持したまま一緒に送ります.
管理画面で必要になる送信規則も実装しました.
たとえば, 無効化されたフィールドを送らず, チェックの外れたチェックボックスも送りません.

ブラウザは, サーバから受け取った HTML を解析し, ページの構造を表す DOM を組み立てます.
HTML の書き方によっては, 解析後の構造がソースの見た目と異なることがあります.
また, ページ内の JavaScript が DOM や入力欄の状態を変更することもあります.

HTML の読み取りには, Go の `golang.org/x/net/html` を使っています.
管理画面には, 解析後のツリーで入力欄がフォームの子孫にならないページが混じっています.
1 つは, フォームが表の直下に置かれている形です.
この形の画面を HTML5 の規則でパースすると, 入力欄がフォームの子孫にならず, フォームをたどっても値が取れませんでした.
もう 1 つは, ソースの時点でフォームが閉じられ, 入力欄が別の表に置かれている形です.
2 つ目の形の画面は, 次のようなものです.

```html
<table><form name="HashForm1"></form></table>
<table>
  <tr><td><input name="arak_ipaddress" value="(IP アドレス)"></td></tr>
</table>
```

どちらも, フォームの子孫からフィールドを取得できなかったときは, DOM の親や兄弟をたどって表を探し, そこから入力欄を拾っています.
この探索は, この機器の管理画面の構造に合わせたもので, ブラウザのフォームへの関連付けを再現するものではありません.

管理画面には, ブラウザで動く JavaScript が埋め込まれていて, そこからチェックボックスをチェック済みにしているページがあります.
その場合, HTML の `checked` 属性がなくても, ブラウザ上ではチェックされています.
チェックボックス自体の記述だけでは, 状態を判断できません.

```html
<script>
  document.HashForm1.grpSeverityCrit.checked = 1;
</script>
```

このパーサは JavaScript を実行しないので, スクリプトによる状態の変更は, 別に読み取る必要があります.
そこで, 管理画面で確認した `.フィールド名.checked = 1` という記述を正規表現で拾い, 対応するチェックボックスをチェック済みとして扱っています.
JavaScript の条件分岐や実行順序を評価しているわけではなく, この対応は確認した代入の書き方に限られます.

同じ名前のフィールドが複数ある箇所もあります.
スマートコンセントの起動遅延は 2 つのコンセントで同じ名前が並ぶので, 出現順で区別します.

### [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp)

ここまでに挙げた HTML の癖は, HTML のソースを読むだけでは見つけにくいです.
実際にどのフィールドが送られるかは, ブラウザが送信するリクエストの内容で確認できます.
そのため, 開発中の調査には, ブラウザを操作する MCP（Model Context Protocol）サーバを使っています.

MCP ツールの設定で, chrome-devtools の MCP サーバを起動し, 起動中の Chrome につなぐようにしました.

開発用の AI エージェントは, ページを移動し, スクリプトを評価し, フォームに入力して送信し, ネットワーク要求の内容を読みます.
`evaluate_script` で `document.querySelectorAll` を使えば, フォームと入力欄が DOM のどこにあるかを確かめられます.
フォームと入力欄の親子関係を調べれば, 入力欄がフォームの外にあることも分かります.
入力欄の `.form` やフォームの `.elements` を見れば, ブラウザがどのフォームに関連付けているかも分かります.
DOM 上の親子関係と, ブラウザのフォームへの関連付けは, 必ずしも一致しません.
関連付けられた入力欄のうち, 実際に何が送信されるかは, 送信されたリクエストで確認します.
現在のチェック状態は, HTML の `checked` 属性ではなく `.checked` プロパティで確認します.

送信されたリクエストも見られます.
`fill_form` と `click` でフォームを送り, `list_network_requests` と `get_network_request` で POST の宛先と本文を読みます.
隠しフィールドの名前, `submit=Apply` の値, セッション ID を含むパスは, ここで確かめました.
URL や POST の本文にはセッション ID や認証情報が含まれることがあるので, 取得した内容の扱いには注意が必要です.
MCP で取得した内容は, エージェントの会話履歴やログに残ることもあります.
17 のページにある 18 の設定グループを調べ, フォーム名とフィールド名を集めて, 属性との対応表を作りました.

ブラウザは GS Pro 500 につながっていて, クリックや送信で設定が変わることがあります.
調査は読み取りだけのページから始め, 書き込みを試すときは元の値を控えておきます.
エージェントに渡すツールも許可リストで絞っています.
ページの一覧, スナップショット, 移動, スクリプトの評価, フォームの入力, クリック, ネットワーク要求の取得といった範囲です.
ただし, スクリプトの評価やクリックは設定を変えられるので, 許可リストは読み取り専用の保証ではありません.

この MCP サーバは開発のための道具です.
Terraform Provider は HTTP クライアントと HTML パーサだけで動くので, 実行にブラウザは要りません.

## Terraform State と GS Pro 500 の設定

### 1 台を 1 つのリソースにする

最初は画面のまとまりに合わせて, 設定, コンセント, ネットワークの 3 つのリソースに分けていました.
いまは 1 台を 1 つの `apc_gspro500` リソースで表しています.

分割していたときも, 各リソースが同じセッションで同じ機器を読んでいました.
この実装では, 一部だけを管理する場合も, 全体の状態を読みます.
1 台の機器にいくつものリソースを並べるより, 1 つのリソースに属性を並べるほうが, 何を管理しているか分かりやすいです.

### 設定属性を Optional と Computed にする

属性は原則として Optional と Computed の両方を立て, `UseStateForUnknown` を付けます.
`.tf` に書いたリソースの設定値は, 実機の設定と区別して config と呼びます.
config に属性を書くと, それが実機への指示になり, 書かなかった属性は GS Pro 500 から読んだ値が state に残ります.
Computed にしておくと, 値が config にないときは Terraform Provider が GS Pro 500 から読んだ値で埋められます.
`UseStateForUnknown` は, 既存の state に値がある場合に, 未知になった計画値を計画時の state の値で補います.
ただし, この補完は, 更新の前後で値が変わらない属性を前提にします.
ほかの設定に連動して変わる属性では, 補完した計画値と適用後の値が食い違う可能性があります.
その食い違いは, 適用のときに `Provider produced inconsistent result after apply` のエラーとして現れることがあります.

config から属性を消しても, 初期化の指示にはなりません.
この実装では, 未指定の属性の計画値に state の値を引き継ぐので, 属性を省略したことだけでは設定の変更を計画しません.

SMTP のパスワードは WriteOnly にして, state にも plan にも残しません.
ただし, GS Pro 500 までの通信は平文の HTTP なので, 送るときにネットワークを流れること自体は変わりません.
WriteOnly の値は state に残らず比較もされないので, パスワードは Terraform の差分として現れません.
ほかの属性に差分がなく, パスワードだけを変えた場合, Update は呼ばれません.

### 空文字と入力欄の欠落を null にする

現行の実装では, 読み取った値を state に入れるとき, ページに入力欄が見つからなかった属性と空文字を null にしています.
Terraform では, 空文字と null は別の値として扱われます.
入力欄の欠落と, 機器側で未設定であることは区別していません.
ページの変更やパースの失敗で入力欄を見落とすと, そのまま null として扱われます.
config で空文字を指定した場合も null に変換すると, 計画値と適用後の state が一致せず, エラーになる可能性があります.

### どの設定グループを送るかと, 何を送るか

Update は, このリソースに置換を伴わない更新が計画されたときに呼ばれます.
そのとき, config と plan を別の用途に使います.

属性を省略した場合, config の値は null になります.
plan の属性値は適用後に期待する値で, この実装では送信する値の取得元として使います.
未指定の Optional と Computed の属性には, 既存の state の値が引き継がれます.
計画値が unknown になる場合は, `UseStateForUnknown` で既知の state の値を使います.

どの設定グループを送るかは, config で決まります.
設定グループは属性名の接頭辞で決まるので, たとえば `network_` で始まる属性を 1 つも書いていなければ, ネットワークの設定グループは送りません.
1 つでも書いていれば, その設定グループを送ります.
グループ内に差分があるかどうかは見ていません.

送る値は plan から取ります.
そのため, 同じ設定グループの中で config に書いていない属性も, state の値で埋めて送ります.
書き戻しが設定グループ単位になるのは, このためです.
計画の後に実機側で値が変わっても, config に書いていない属性は plan の値で上書きされます.

WriteOnly のパスワードだけは, plan に値が残らないので config から取ります.

### Create と Delete の意味

このリソースが扱うのは, 既存の GS Pro 500 の設定です.
機器そのものの作成や削除はしません.
そこで Create は, GS Pro 500 の設定を取り込み, config に書かれた値だけを適用する操作にしました.
Update と違い, 指定のない属性は取得したフォームの値のまま送ります.
Delete は state から消すだけで, GS Pro 500 の設定は変えません.

`terraform destroy` でも GS Pro 500 の設定は初期化しません.

## [Self-hosted agents](https://developer.hashicorp.com/validated-designs/terraform/administration-guide/self-hosted-agents)

Terraform Provider は Terraform のプラグインで, plan と apply を実行するホストの上で動きます.
GS Pro 500 へはそのホストから HTTP で接続するので, 実行する場所は GS Pro 500 に届くネットワークでなければなりません.
GS Pro 500 のアドレスは LAN の中にしかありません.

state と run は HCP Terraform の Terraform Workspace で管理し, 作業用の PC では plan と apply を実行しません.
HCP Terraform の Remote 実行モードでは, run は HashiCorp が用意する実行環境で動きます.
その実行環境は自宅の LAN には届きません.
そこで, LAN の内側に tfc-agent を置き, その上で run を実行しています.
HCP Terraform 側では, Terraform Workspace の実行モードを Agent にしています.
tfc-agent は HCP Terraform との通信を外向きの HTTPS で行うので, HCP Terraform から接続を受けるためのポート開放は要りません.

![HCP Terraform, LAN 内の tfc-agent, GS Pro 500 の関係](/images/2026-02-22-terraform-provider-apc-agents.svg)

Terraform Workspace は GitHub のリポジトリと連携していて, PR では適用を伴わない plan が走ります.
Auto-apply を有効にしているので, default branch へのマージ後は plan を経て apply が走ります.
結果は Slack に通知する設定にしています.

GS Pro 500 の設定は, Homelab 用の Terraform Workspace で管理しています.
以下では, organization と Terraform Workspace の名前を, 例示用の値に置き換えています.
Terraform Provider は HCP Terraform のプライベートレジストリから取得し, 接続先と認証情報は Terraform Workspace の変数で渡しています.

```hcl
terraform {
  cloud {
    organization = "example-org"

    workspaces {
      name = "example-workspace"
    }
  }

  required_providers {
    apc = {
      source  = "app.terraform.io/example-org/apc"
      version = "~> 0.3"
    }
  }
}
```

![plan / apply 時の認証情報と state の流れ](/images/2026-02-22-terraform-provider-apc-credentials.svg)

この構成では, Terraform Provider を HCP Terraform のプライベートレジストリ経由で配布するので, ビルドしたバイナリの配布情報をレジストリに登録しています.

ビルドと登録は, 自前の GitHub Actions のワークフローで行っています.
GitHub のリポジトリにタグを push するとワークフローが起動し, GoReleaser でバイナリのアーカイブを作り, チェックサムファイルに GPG 署名します.
そして, HCP Terraform のプライベートレジストリにバージョンとプラットフォームごとの配布情報を登録します.
tfc-agent が起動する Terraform は, レジストリの配布情報を使って Terraform Provider を取得します.

tfc-agent は HashiCorp が配布しているバイナリで, リリースページで公開されている zip を取得して使います.
NixOS のホストでは, その zip を取得する derivation を自分で書き, バージョンを固定しています.
tfc-agent は systemd-nspawn のコンテナの中で動かしています.
tfc-agent の上では Terraform と Terraform Provider が動くので, ホストへの影響を抑えるためにコンテナに入れています.
コンテナはホストのネットワークを共有するので, コンテナ化しても LAN へのアクセスは制限されません.
tfc-agent のトークンは sops-nix でホストに復号し, 読み取り専用でコンテナに渡しています.

PR の plan でも, Provider やデータソースのコードが LAN 内で実行されます.
run を起動できる変更と利用者は, 信頼できる範囲に限る必要があります.

公開の Terraform レジストリに置いていないのは, 対象が自宅の GS Pro 500 1 台に限られ, 広く配る必要がないためです.

## メール通知を中継で通す

GS Pro 500 側のメール通知設定も, この Terraform Provider で管理しています.
停電やバッテリの異常をメールで受け取りたいのですが, GS Pro 500 から利用したいメールサービスへは直接接続できませんでした.

GS Pro 500 から iCloud の SMTP サーバへ直接送ろうとすると, TLS 接続に失敗しました.
原因は特定できていませんが, TLS のバージョンや暗号スイートの互換性を疑い, LAN の中に SMTP の中継を置きました.
GS Pro 500 は中継にだけ接続し, 中継が上流のメールサービスへ転送します.

![UPS から SMTP の中継を経て iCloud の SMTP へ送る流れ](/images/2026-02-22-terraform-provider-apc-mail-relay.svg)

- GS Pro 500 の設定では, 中継へポート 25 で STARTTLS を使い, 認証はしないようにします.
- 中継から上流へは, TLS 1.2 以上を必須にして, SASL 認証を使います.

中継には Postfix を使い, その設定を NixOS のモジュールとして書きました.
受信側は, GS Pro 500 との互換性を考慮し, 古い TLS も受け入れる設定にしています.
中継は STARTTLS を提供しますが, TLS を必須にしていないので, 平文での接続も受け入れます.
中継の SMTP サーバは LAN 側のアドレスで待ち受けます.
GS Pro 500 以外の接続元からの中継は受け付けません.
ただし, この制限で盗聴や改ざんを防げるわけではありません.
送信元のアドレスに使えるドメインも絞り, 中継専用にして, ローカルへの配送はしません.
上流のパスワードは NixOS の秘密管理から `/run` 以下に配置し, 読み取り権限を制限しています.

Terraform Provider からは, メールの設定グループで通知の送信元と宛先, 本文の形式を設定します.

## 制約と残課題

- Terraform Provider と管理画面の通信は HTTP なので, 認証情報と設定値は LAN を平文で流れます.
  管理用のネットワークの分離やアクセス制限が要ります.
- Read は毎回 18 の設定グループすべてを GS Pro 500 から読み直すので, そのたびに複数ページへの HTTP リクエストが発生します.
- 接続先や認証情報, セッションといったクライアント状態はプロセスのシングルトンに置き, Configure のたびに上書きしています.
  同じプロセスで複数の Provider 設定を使うと接続先や認証情報が混ざるおそれがあるため, Provider alias を使った複数台の管理には対応していません.
- この Terraform Provider で設定を管理しても, バッテリの保守は別に必要です.
  交換時期はメーカーの案内に従って確認します.

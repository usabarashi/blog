全文検索は, 語が一致する箇所を見つけるには強い一方で, 言い換えられた質問には弱いままでした.
エージェントからの質問は, 本に書かれている語と一致するとは限りません.
そこで, 本文をベクトル化し, 意味の近さでも検索できるようにしました.
全文検索の仕組みは[ビューワーと MCP の記事](epub-viewer-and-mcp.html)に書きました.
ここでは, ベクトル検索と, 2 つの検索を混ぜる話を書きます.

## 全文検索だけでは足りない

今回の全文検索は, 検索語と本文中の語の一致をもとに候補を探します.
言い換えや表記揺れは取りこぼしやすく, 日本語では語の切れ目も曖昧です.

ベクトル検索は, 文章を数値の並びに変え, その距離で意味の近さを測ります.
本の語と質問の語が違っても, 意味が近ければ候補になります.
ただし, 識別子や数値の完全一致は苦手です.

どちらか一方ではなく, 2 つの順位を混ぜることにしました.

| 検索 | 強いところ | 弱いところ |
|---|---|---|
| 全文検索 (FTS5/BM25) | 語の一致, 識別子, トークンとして切り出せる固有名詞 | 言い換え, 表記揺れ, 日本語の語の切れ目 |
| ベクトル検索 | 意味の近さ, 言い換え | 完全一致, 数値, 珍しい識別子 |
| ハイブリッド | 両方の候補を順位で混ぜる | どちらも外すと見つからない |

## チャンクに分ける

章の本文はそのままでは長すぎるので, 埋め込みの単位に分割します.
分割した本文のまとまりを, ここではチャンクと呼びます.
段落の切れ目で区切り, 500 文字ほどになるまでまとめます.
1 つの段落が 500 文字を超える場合は, その段落だけで 1 つのチャンクにします.
隣り合うチャンクの重複は, 最初は入れていません.
500 文字は, 検索結果として引用しやすい長さです.
モデルの上限はトークン数で決まるので, 通常のチャンクには余裕がありますが, 1 つの段落が長い場合は超える可能性があります.

チャンクには, 書籍, 章, 章内でのチャンクの順番を持たせます.
検索結果と引用の単位が, このチャンクになります.

## 埋め込みベクトルを計算する

埋め込みベクトルは, ホスト上の Ollama の bge-m3 で計算します.
bge-m3 は日本語と英語を同じベクトル空間で扱え, 1024 次元のベクトルを返します.
最初は英語向けのモデルを想定していましたが, 日本語の本も扱うため, 多言語の bge-m3 に切り替えました.
モデルを変えると, すべてのチャンクの埋め込みを作り直す必要があります.
ベクトルはモデルをまたいで比較できないためです.
モデルごとに, テキストをベクトル空間内のどの位置に対応させるかが異なります.
次元数が同じでも, 座標の意味が揃っていなければ, ベクトル間の距離を比べても意味がありません.
検索では, 保存したチャンクと同じモデルでクエリも埋め込む必要があります.
次元が変わるモデルでは, ベクトルを保存する表も作り直す必要があります.

[![BAAI/bge-m3 のモデルカード](https://cdn-thumbnails.huggingface.co/social-thumbnails/models/BAAI/bge-m3.png)](https://huggingface.co/BAAI/bge-m3)

Ollama は OpenAI 互換の `/v1/embeddings` を提供します.
同じ OpenAI 互換 API を提供するランタイムなら, クライアントの基本構造を変えずに切り替えられます.

クラウドの API は使わず, ホストの中だけで完結します.
蔵書の本文を外部の API に送らずに済むのが, 自前で動かす大きな理由です.
本を取り込む際には各チャンクの埋め込みを計算し, モデルを変更する際には全チャンク分を再計算します.
従量課金の API では, こうした計算量に応じて費用がかかります.
API キーの管理も, 外部サービスの停止の影響も避けられます.
その代わり, 埋め込みの速度はホストの計算資源に左右されます.

埋め込みはチャンクごとに 1 回の HTTP リクエストで計算します.
まとめて送ると 1 回の応答待ちが長くなり, タイムアウトしやすくなりました.
チャンクごとに送れば, 失敗したチャンクだけをやり直せます.

失敗の回数と最後のエラーは SQLite に記録し, 同じチャンクを無限に再試行しないようにしています.
埋め込みが済んでいないチャンクは, 後からまとめて埋めるバックフィルで処理します.

クエリの埋め込みは, 同じ検索語と同じモデルなら SQLite のキャッシュを使います.
エージェントが同じ質問を繰り返すときに, 埋め込みの計算を省けます.

## 保存と近傍探索

ベクトルは [sqlite-vec](https://github.com/asg017/sqlite-vec) の `vec0` 仮想テーブルに保存します.
次元は 1024 で固定です.

```
CREATE VIRTUAL TABLE chunk_vec USING vec0 (
  chunk_id TEXT PRIMARY KEY,
  embedding FLOAT[1024]
);
```

ベクトルは float32 のバイト列としてそのまま入れます.
本文は `chunk` テーブルに, 全文検索用の写しは FTS5 の `chunk_fts` に置きます.

近傍探索は, クエリのベクトルに近いチャンクを距離順に返します.
この構成では, sqlite-vec は近似索引を使わず, 保存したベクトルを全件走査して近傍を探します.
個人のライブラリの規模では許容できますが, チャンクが増えるほど検索は遅くなります.

1024 次元の float32 は 4 KiB です.
500 文字程度の本文に対して, ベクトルの値だけでこの大きさを使います.

## 密と疎の順位を混ぜる

検索は, 密 (ベクトル) と疎 (全文検索) の 2 つの経路で候補を取ります.
密は, クエリの埋め込みと `chunk_vec` の近傍探索です.
疎は, FTS5 の BM25 です.

それぞれの上位候補を, RRF (Reciprocal Rank Fusion) で 1 つの順位にまとめます.
RRF は, 各検索での順位に応じた値を候補ごとに足し合わせます.
今回は定数を 60 とし, 順位を 1 位から数えて `1 / (60 + 順位)` を使います.
その検索で候補に入らなかったチャンクは, 加算しません.
元のスコアではなく順位を使うので, 2 つの検索のスコアの尺度をそろえる必要がありません.

候補は, 各経路で, 最終的に返す件数の約 4 倍を取ります.
各経路では最終件数の外にある候補も, 両方の順位を合わせると上位に入る可能性があるためです.

抜粋は, FTS5 の `snippet` が取れればそれを使い, 取れなければチャンクの先頭を使います.

## MCP から使う

検索は MCP の `search_library` から呼べます.
返るのは, チャンクの本文 (抜粋), 書籍, 章, スコアです.
`get_chunk_context` を使えば, そのチャンクの前後の本文も取れます.

エージェントは, 本文を引用するときに, 検索結果の書籍名と章を出典として示せます.
回答を作るのはエージェントで, このサービスは根拠と出典を返すだけです.
ブラウザの検索も, 同じバックエンドの検索を使っています.

設計についてコーディングエージェントと壁打ちするときも, 書籍の記述を根拠にした会話ができます.
検索語によっては, 密と疎のどちらかだけが当たります.
それでも, 2 つの候補を混ぜることで, 語の一致と言い換えの両方を拾いやすくなります.

## 雑感

エージェントに雑な聞き方をしても, MCP 経由で文脈に合った本の記述を探してくれるのが助かっています.
調べたいことが漠然としていても, 検索語を正確に組み立てずに関連する本文を引いてきてもらえます.
自分で検索語を試すというより, 会話の流れに沿って蔵書から候補を挙げてもらう感覚です.
